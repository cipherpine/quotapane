## 5. The step-6 failure — analysis, no fix applied

**What the check does** (`tools/release-verify.sh:104`):

```sh
V="$("$BIN" --version 2>&1)" && grep -q "${TAG#v}" <<<"$V" && "$BIN" --help >/dev/null 2>&1 \
  && pass "step 6: shipped CLI runs ($V)" || fail "step 6: shipped CLI ($V)"
```

With `TAG=v1.5.0-rc.1`, `${TAG#v}` is `1.5.0-rc.1`. The shipped binary prints
`quotapane-cli 1.5.0` — the crate version, which is what
`env!("CARGO_PKG_VERSION")` must print, and which is *correct*: the rc tag
deliberately points at the exact commit that becomes v1.5.0, so its crate
version has no `-rc.1` suffix. The grep therefore cannot match, and **no
correctly-built release can pass step 6 under a prerelease tag.**

Evidence that the artifact itself is sound — the shipped Windows CLI runs and
answers both flags:

```
$ x_win/.../quotapane-cli.exe --version
quotapane-cli 1.5.0
$ x_win/.../quotapane-cli.exe --help    # exit 0, full help printed (excerpt in §6)
```

So the binary satisfies both halves of step 6's *intent* — it runs, and it
reports the version the release carries. Only the tag-shaped equality assertion
fails.

**Why this is surfacing now.** `tools/release-verify.sh` was authored in M11
(2026-08-03), *after* v1.4.1 shipped (2026-08-01). Its rc path has therefore
never been executed before: `v1.5.0-rc.1` is the first prerelease tag this tool
has ever been pointed at. The gap is in the tool's rc handling, not in this
release.

**Mechanical note, offered as fact and not as a decision:** at the final tag
`v1.5.0`, `${TAG#v}` would be `1.5.0` and this same assertion would match the
binary's output. Whether that makes the rc verdict acceptable, whether step 6
should be taught about prerelease suffixes, and whether the M11
release-verify standard needs amending are top-tier calls recorded in
DECISIONS.md — **not this session's**. `tools/release-verify.sh` was not
edited, the run was not repeated under a modified invocation, and the manual
six-step standard was not improvised in its place.
